# Math-AI — Database Design Explained

> Audience: developers and AI agents working on `math-svr`.
> Source of truth: SQL files under `/migrations/`. When this document and a
> migration disagree, the migration wins — open a PR to update this doc.

This document explains *why* the schema looks the way it does, not just *what*
each column holds. Pair it with `/.claude/CLAUDE.md` (architectural guide) and
the migration files themselves.

---

## 1. Core business concepts

Math-AI is an AI-powered Math quiz platform for **Vietnamese elementary
school children (Grades 1–5)**. The product is parent-operated:

- A **user** is the *adult account holder* (usually a parent or guardian).
  Identified by phone number; no password — authentication is intended to be
  OTP / device-trust based.
- A **profile** is a *child*. A user can own multiple profiles so a family
  with several children manages each child's learning separately under one
  account.
- The **curriculum** mirrors Vietnam's Ministry of Education structure:
  `program → grade → semester`. A child sits on exactly one
  `(grade, semester)` pair at any moment.
- A **quiz** is a unit of learning content generated by AI to satisfy a
  specific *learning purpose* (assessment, practice, exam, …). The system
  stores both the generated quiz and the AI's review of how the child did.

Four headlines you should keep in mind while reading every section below:

| # | Headline | Practical impact |
|---|---|---|
| 1 | **Passwordless** — no credentials column anywhere | Login flow is phone-based (OTP) + device trust (`ma_devices.is_verified`). Don't add a `password` column. |
| 2 | **One user, many children** | All child-scoped data should ultimately attach to a *profile*, not the user. (See §6 — `ma_quizzes` currently breaks this; flagged as a design gap.) |
| 3 | **Curriculum data is bilingual** | Every reference table has a sibling `*_translations` table. Default language is `vn`. |
| 4 | **AI is a peer of the schema** | The quiz table stores AI's generated content (`questions`, `answers`) *and* the AI's review (`ai_review`, `ai_detect_grade`). The DB is the AI's blackboard, not just the human's. |

## 3. Relationship diagram

UUIDs are used as the public ID for every row. There are **no foreign-key
constraints** in the schema — integrity is enforced at the application
layer inside `UnitOfWork` blocks (see §7.1).

```
                  ma_users (parent / guardian)
                  ──────────────────────────────
                  id, user_id, phone, email, …
                       │  1
                       │
       ┌───────────────┼──────────────┬──────────────┬──────────────┐
       │ N             │ N            │ N            │ N            │
       ▼               ▼              ▼              ▼              ▼
  ma_aliases     ma_devices     ma_login_logs   ma_profiles     ma_quizzes
  (lookup keys) (device trust) (audit trail)  (children)    (AI content)
                                                  │ 1
                                                  ▼
                                            (grade_id, semester_id)
                                                  │
                  ┌───────────────────────────────┴───────────────────────┐
                  ▼                                                       ▼
              ma_grades                                              ma_semesters
              ──────────                                             ────────────
              id, grade_id, label, …                                 id, semester_id, …
                  │ 1                                                    │ 1
                  ▼ N                                                    ▼ N
            ma_grade_translations                              ma_semester_translations
            (language, label, description)                     (language, name, description)


              ma_programs    ──┐
              ──────────       │ 1 → N
              id, program_id, … ├────► ma_program_translations
                                       (language, label, description)

              ma_contact_us         (no relation; standalone inbox)
```

**Observation:** `ma_programs` does not yet link to anything — there's no
`program_id` column on `ma_profiles` or `ma_quizzes`. This is a known design
gap (see §6).

## 4. Table-by-table walkthrough

Every table inherits a common audit/visibility skeleton — only the
domain-specific columns are explained here.

> **Common columns** present on (almost) every table:
> `id` (internal `BIGINT` PK), `<entity>_id` (external `CHAR(36)` UUID),
> `note` (free-form admin note), **`status`** (system visibility:
> `ACTIVE`/`INACTIVE`), **`<entity>_status`** (business lifecycle:
> `ACTIVE`/`INACTIVE`/`DELETED`), `create_id`, `create_dt`, `modify_id`,
> `modify_dt`, `deleted_dt`.
>
> *Why both `status` and `<entity>_status`?* `status` is a kill-switch for
> ops (hide a row without changing business state); `<entity>_status` is the
> domain truth (DELETED = soft-deleted by the user). Reads must filter on
> **both**.

### 4.1 Identity & access

#### `ma_users` — the adult account holder
| Column | Notes |
|---|---|
| `phone` | `NOT NULL`. Primary login key. |
| `email` | nullable; optional contact channel. |
| `user_status` | business lifecycle |

**No `password` column.** Authentication is intended to be passwordless: the
user proves they hold the phone via OTP (delivered through the SMS adapter),
and the device is then trusted via `ma_devices.is_verified`.

#### `ma_aliases` — alternate lookup keys
| Column | Notes |
|---|---|
| `user_id` | FK-by-convention to `ma_users.user_id` |
| `aka` | the lookup key itself (a phone number, or an email) |
| `alias_status` | business lifecycle |

Each registered key (phone + each verified email) becomes one row. The
`CreateUser` command writes one alias for the phone, and one more for the
email if provided. This shape lets the system support "log in with phone
OR email" by querying a single table instead of fanning out to `ma_users`
on both columns.

Practically, you'd index by `aka` in the future when login by email is
exercised at scale — the current schema declares no such index.

#### `ma_devices` — device trust + push delivery
| Column | Notes |
|---|---|
| `user_id` | nullable — a device row may exist before login (anonymous install) |
| `device_uuid` | mobile-OS-supplied unique identifier |
| `device_name` | human-readable (e.g. "Quoc's iPhone 14") |
| `device_push_token` | nullable; for FCM/APNs push via the notification adapter |
| `is_verified` | flips to 1 after the device completes its first OTP login |

The mobile client registers the device on first launch, then completes
verification at the end of the first login flow.

#### `ma_login_logs` — audit trail
| Column | Notes |
|---|---|
| `user_id`, `ip_address`, `device_uuid`, `token` | full attribution of a successful login |
| `login_log_status` | useful for marking a session revoked |

Pure write-then-read append log. Used by security/audit, not by hot paths.

### 4.2 Learner identity

#### `ma_profiles` — the child
| Column | Notes |
|---|---|
| `user_id` | the **parent's** id — multiple profiles per user is the central design choice |
| `name` | the child's display name |
| `avatar_key` | object-storage key (S3) for the avatar image |
| `dob` | child's date of birth (used for age-appropriate UI / display) |
| `grade_id` | current grade — `NOT NULL` (a child must always sit on a grade) |
| `semester_id` | current semester within the grade — `NOT NULL` |
| `profile_status` | business lifecycle |

**Design rule:** the child progresses by *updating* `grade_id` /
`semester_id` on the same row, not by creating new ones. The schema does
not preserve history of which grades/semesters a child has been through.
If grade history is needed later, introduce a separate
`ma_profile_grade_history` table — do not break the single-row invariant.

### 4.3 Curriculum reference

#### Pattern (applies to programs, grades, semesters)

Three reference tables (`ma_programs`, `ma_grades`, `ma_semesters`) hold the
canonical English label and a `display_order`. A sibling `*_translations`
table holds per-language strings (`language` column; today `vn` and `en`).

```
ma_<thing>                       ma_<thing>_translations
─────────────                    ─────────────────────────
<thing>_id   CHAR(36) UNIQUE     <thing>_translation_id CHAR(36)
label        VARCHAR(128)        <thing>_id            CHAR(36)   ← link
description  VARCHAR(128)        language              VARCHAR(10)
image_key    VARCHAR(128)        label / name          VARCHAR
display_order TINYINT            description           VARCHAR / TEXT
```

Why split? Two reasons:
1. **i18n** — Vietnamese strings need utf8mb4; rather than store one column
   per language on the parent row (brittle as languages grow), the
   translation table is the long-term-clean shape.
2. **Editable per-locale UX strings** — the marketing/CS team can tweak
   Vietnamese labels without touching the structural row.

Note: `ma_grade_translations` and `ma_semester_translations` declare
`UNIQUE KEY (<thing>_id, language)`. `ma_program_translations` **does
not** — adding it is a recommended cleanup (otherwise inserting two `vn`
rows for the same program is allowed).

#### `ma_programs` — Vietnam's MoET curricula
The five official elementary programs ("bộ sách giáo khoa"):

| English label (in `label`) | Vietnamese (in `*_translations`) |
|---|---|
| Connecting Knowledge with Life | Kết nối tri thức với cuộc sống |
| For Equality and Democracy in Education | Vì sự bình đẳng và dân chủ trong giáo dục |
| Learning Together for Competence Development | Cùng học để phát triển năng lực |
| Creative Horizons | Chân trời sáng tạo |
| Kite | Cánh diều |

Schools in Vietnam choose one of these books. The platform exposes all five
so parents can pick the one matching their child's school.

#### `ma_grades` — Grade 1 through Grade 5
Pure enumeration. `display_order` matches the numeric grade.

#### `ma_semesters` — checkpoints within a school year
Today there are four: mid-term 1, end-term 1, mid-term 2, end-term 2 — see
the commented-out seed data in `008_ma_semesters_table.sql`. Each is a
discrete unit a child progresses through.

### 4.4 Learning content

#### `ma_quizzes` — the AI-generated quiz
| Column | Notes |
|---|---|
| `user_id` | currently the *parent's* id (see gap §6.1) |
| `type` | `ASSESSMENT` \| `PRACTICE` \| `EXAM` (the column comment lists these; more may be added) |
| `questions` | `LONGTEXT` — JSON payload of generated questions |
| `answers` | `LONGTEXT` — JSON payload of the child's submitted answers |
| `ai_review` | `VARCHAR(255)` — the AI's qualitative feedback on how the child did |
| `ai_detect_grade` | `VARCHAR(16)` — the grade level the AI inferred from performance |
| `quiz_status` | business lifecycle |

This table is the AI's working surface. It is intentionally **not**
relationally modeled at the per-question level — questions and answers are
opaque JSON blobs that the generation/review pipelines parse on the way in
and on the way out.

Trade-off: this is fast to ship and AI-pipeline-friendly, but limits what
you can query without parsing JSON. See §6.2 for the impact on the
PRACTICE flow.

### 4.5 Customer service

#### `ma_contact_us` — "contact us" form inbox
Standalone. `user_id` is nullable so anonymous visitors can submit.
Replies/responses are not modeled — this is a pure inbox today.

## 5. End-to-end flows

### 5.1 Onboarding (parent → first quiz)

```
1. App install
   └─► POST /devices/register  (anonymous; ma_devices row, user_id NULL)

2. Phone entry + OTP (passwordless login)
   └─► POST /auth/request-otp  (SMS adapter via Twilio)
       └─► POST /auth/verify-otp
           ├─► creates / updates ma_users  (phone, email?)
           ├─► creates ma_aliases rows (one per registered key)
           ├─► links the device: ma_devices.user_id = <user>, is_verified = 1
           └─► appends ma_login_logs row

3. Create the first child profile
   └─► POST /profiles/create
       └─► ma_profiles row: name, dob, grade_id, semester_id (parent picks)

4. Pick a curriculum (program)
   └─► GET /programs?lang=vn       (JOIN ma_programs + ma_program_translations)
   └─► (today: parent selection is held client-side; no program_id is
       persisted to the profile — see gap §6.3)

5. Generate the first ASSESSMENT quiz
   └─► POST /quizzes/generate { profile_id, type: ASSESSMENT }
       ├─► AI pipeline reads profile.grade + profile.semester
       ├─► AI generates questions[] (JSON)
       └─► writes ma_quizzes row with type=ASSESSMENT, answers=null
```

### 5.2 Daily-use practice loop

```
1. Parent opens the app, selects which child to work with.
   └─► GET /profiles?user_id=<parent>   (lists all children of that parent)

2. Parent chooses "Practice".
   └─► POST /quizzes/generate { profile_id, type: PRACTICE }

   The PRACTICE generator should preferentially re-surface
   questions the child previously got wrong. This requires
   looking at prior ma_quizzes rows for the profile and
   parsing answers[] — see §6.2.

3. Child answers in the app.
   └─► POST /quizzes/<quiz_id>/submit { answers }
       ├─► updates ma_quizzes.answers
       ├─► AI scores and writes ma_quizzes.ai_review
       └─► AI may update ma_quizzes.ai_detect_grade

4. Parent reviews progress.
   └─► GET /quizzes?profile_id=...&type=...   (history)
```

### 5.3 Grade progression

When the school year advances (or the AI's `ai_detect_grade` suggests the
child has outgrown their current grade):

```
PATCH /profiles/<profile_id> { grade_id, semester_id }
   └─► UPDATE ma_profiles SET grade_id=?, semester_id=? WHERE profile_id=?
```

The previous `(grade, semester)` is **not** preserved — the row mutates in
place. If a future feature needs to chart historical progression, model it
as a separate event-log table.

## 6. Known design decisions, trade-offs, and gaps

Each item is something a future implementer should know about *before*
adding a feature in this area. Some are intentional trade-offs; some are
gaps to be closed.

### 6.1 `ma_quizzes.user_id` instead of `profile_id` — **GAP**

A user can own several children profiles, but the current schema attributes
a quiz to the *user*, not the *profile*. This makes it impossible to
correctly answer "list this child's quizzes" without an additional column.

**Recommended fix:** add `profile_id CHAR(36) NOT NULL` to `ma_quizzes`.
Keep `user_id` as a denormalized convenience (or drop it and JOIN through
`ma_profiles`). Migration must:
1. Add the column nullable.
2. Backfill from `ma_profiles` (any profile of the quiz's user — manual
   intervention may be required if a user has > 1 profile).
3. Tighten to `NOT NULL`.

### 6.2 PRACTICE-on-incorrect-answers is not query-friendly — **GAP**

The product requires PRACTICE quizzes to revisit *previously incorrect
answers*. With `questions` and `answers` stored as opaque `LONGTEXT` JSON
blobs, the only way to find incorrect answers is to load every prior quiz
for the child and parse JSON in Go.

**Two alternative shapes** to consider when this becomes a hot path:

- **Per-question result table** (relational):
  `ma_quiz_question_results(profile_id, quiz_id, question_key, is_correct, …)`.
  Cleanest for analytics and the PRACTICE generator, but doubles the write
  cost per quiz submission.
- **JSON columns + generated columns / functional indexes** (MySQL 8 native):
  store JSON but extract `incorrect_count` and pick-list of incorrect
  question keys into virtual columns indexed for query. Less write overhead,
  more SQL acrobatics.

Pick when the PRACTICE generator is built; revisit this section when
making the call.

### 6.3 `ma_profiles` does not pin a `program_id` — **GAP**

A child attends a school that uses *one* of the five curricula. Today the
profile row holds `grade_id` and `semester_id` but not `program_id`. The
choice is currently only carried client-side (or is implicit in quiz
prompts).

**Recommended fix:** add `program_id CHAR(36) NULL` initially, then
`NOT NULL` once the client backfills. Once present, the AI quiz generator
can lean on it directly.

### 6.4 `ai_review VARCHAR(255)` is undersized — **GAP**

The AI review is the qualitative feedback shown to parents — 255 chars is
one short paragraph at most. As soon as the review goes beyond a single
sentence, switch to `TEXT` or `LONGTEXT`.

### 6.5 No foreign-key constraints — **INTENTIONAL**

The schema declares no `FOREIGN KEY`s. Cross-table integrity is enforced
inside `UnitOfWork` blocks in the application layer. Rationale:
- Easy migrations / table renames.
- Soft-delete + hard-delete coexist without cascading-delete surprises.
- The system never bulk-loads — every write is going through Go code.

Consequence: orphans can exist if a developer writes outside the
`UnitOfWork` discipline. Code review must enforce that any DELETE that
removes a parent also removes children (look at
`ForceDeleteUserCommandHandler` for the canonical pattern: children first,
then parent).

### 6.6 Dual `status` columns — **INTENTIONAL**

Every table carries both:
- `status` — system visibility (`ACTIVE` / `INACTIVE`). Used to ops-hide a
  row without touching business state.
- `<entity>_status` — business lifecycle (`ACTIVE` / `INACTIVE` /
  `DELETED`). Used by soft-delete and by lifecycle features (suspended
  accounts, etc.).

**Reads MUST filter on both.** The canonical filter helpers live next to
each repository: `userActiveWhere` + `userActiveArgs()` in
`internal/infrastructure/persistence/mysql/repositories/user_repository.go`.

### 6.7 Internal `BIGINT id` + external `CHAR(36) <entity>_id` — **INTENTIONAL**

Each row has two primary identifiers:
- `id BIGINT UNSIGNED AUTO_INCREMENT` — used internally (joins, FKs if added,
  pool affinity). Never returned to the client.
- `<entity>_id CHAR(36) UNIQUE` — the UUID exposed via the API.

Rationale: clients can hold stable UUIDs across environments and data
migrations, while internal joins stay cheap on bigint indexes. Don't expose
the internal `id` — it leaks ordering and counts.

### 6.8 Soft delete + hard delete coexist — **INTENTIONAL**

Two endpoints per aggregate:
- `POST /<aggregate>/soft-delete` →
  `MarkStatusByUserId(..., DELETED)` on parent + children. Row stays in DB.
- `POST /<aggregate>/force-delete` → physical `DELETE`, children first.

Soft is the user-visible action. Hard is for GDPR-style erasure / admin
cleanup. Both go through a `UnitOfWork`.

### 6.9 Translation tables are bilingual today, multilingual-ready — **INTENTIONAL**

Schema supports any `language VARCHAR(10)` value. Only `vn` (default) and
`en` are seeded. The unique key on `(<thing>_id, language)` (where present)
makes one row per language per entity, so adding a third language is a
backfill, not a schema change.

### 6.10 No partitioning or sharding strategy — **INTENTIONAL FOR NOW**

`ma_quizzes` will grow fastest (one row per quiz attempt). At today's
scale a single InnoDB table is fine. Plan a re-think when row count
crosses ~100M or daily inserts exceed write-buffer flush capacity. Most
likely path: shard by `user_id` hash, or move the quiz `questions`/`answers`
JSON blobs to object storage and store only metadata in MySQL.

### 6.11 Indexing is minimal — **GAP (future work)**

The migrations currently only declare:
- Primary keys.
- `UNIQUE` on every external UUID (`<entity>_id`).
- `UNIQUE (<entity>_id, language)` on grade and semester translations.

For production read patterns, additional indexes will pay off:

| Table | Likely index | Why |
|---|---|---|
| `ma_users` | `(phone)` UNIQUE | login lookup |
| `ma_aliases` | `(aka)`, `(user_id)` | alt login & "all aliases for user" |
| `ma_devices` | `(user_id)`, `(device_uuid)` | per-user device list, device trust |
| `ma_login_logs` | `(user_id, create_dt)` | audit time-series |
| `ma_profiles` | `(user_id)` | "list this parent's kids" — the primary hot read |
| `ma_quizzes` | `(user_id, create_dt)`, `(type)` | history + filtering |
| `*_translations` | `(<thing>_id, language)` | translation lookup |

Add these as a focused migration when load testing surfaces the cost.

### 6.12 `utf8mb4` collation `0900_ai_ci` everywhere — **INTENTIONAL**

Two reasons:
- Vietnamese diacritics require utf8mb4 (basic utf8 is 3-byte and breaks).
- `0900_ai_ci` (accent-insensitive, case-insensitive) lets a search for
  "lop 1" match "Lớp 1". The connection-level collation in
  `internal/infrastructure/database/database.go` matches.

Don't override per-table; inherit from the schema-level default.

### 6.13 `DATETIME(6)` microsecond precision — **INTENTIONAL**

Microsecond precision is needed to:
- Disambiguate near-simultaneous events for audit (`ma_login_logs`).
- Match Go's `time.Time` resolution after a round trip.

Stored as UTC; rendered in the user's timezone by the client.

## 7. Architectural decisions that affect schema work

### 7.1 Integrity is enforced in `UnitOfWork`, not by FKs

Every command that touches > 1 table runs inside `transaction.UnitOfWork.Do`.
See `internal/application/command/user/create_user_command.go` for the
canonical example: it inserts the user *and* its alias rows inside one
transaction.

When adding a feature, ask "does this touch more than one table?" — if yes,
write it as a command and make the UnitOfWork run both writes. Don't fan
out from a handler.

### 7.2 Migrations are forward-only

`internal/infrastructure/database/migration.go` tracks applied versions in
the `schema_migrations` table and applies pending files lexicographically.
There is **no down-migration**. To revert a change, write a new
forward-migration that undoes it.

File naming: `NNN_ma_<entity>_<action>.sql` (zero-padded, lexicographic
order). Increment from the highest existing number.

### 7.3 Schema lockstep with code

When you change a table, the following move in lockstep — same commit:

| Touch | Files to update |
|---|---|
| Add a column | migration + `<entity>Columns` + `scanX` + `models/<entity>.go` + domain getter/setter + `ModelToDomain` + DTO mapping |
| Add a status code | `code.go` + `message_en.go` + `message_vn.go` |
| Add a translation | new row in `<thing>_translations` per language |

Failing to update any one of these creates a silent bug. See `/.claude/CLAUDE.md`
§6 for the full lockstep table.

## 8. Glossary

| Term | Meaning |
|---|---|
| **User** | The adult account holder (parent / guardian). Authenticated by phone. |
| **Profile** | A child managed by a user. Pinned to one `(grade, semester)` at a time. |

## 9. Adding a new table — checklist

A condensed version of the recipe in `/.claude/CLAUDE.md` §7, focused on the
DB side:

- [ ] **Pick a name with the `ma_` prefix.**
- [ ] **Inherit the audit skeleton** (`id`, `<entity>_id`, `note`,
      `status`, `<entity>_status`, `create_id`, `create_dt`, `modify_id`,
      `modify_dt`, `deleted_dt`).
- [ ] **Declare `id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY` and
      `<entity>_id CHAR(36) NOT NULL UNIQUE`.**
- [ ] **No FK constraints.** Document parent-child relations in this file
      and enforce in `UnitOfWork`.
- [ ] **Use `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci`.**
- [ ] **Use `DATETIME(6)`** for all timestamps.
- [ ] **If user-facing reference data → add a sibling `*_translations`
      table** with `(<entity>_id, language)` UNIQUE.
- [ ] **Update this document** with the new aggregate group and any new
      cross-table relations.
- [ ] **Migration filename:** `NNN_ma_<entity>_table.sql`, sequential.
